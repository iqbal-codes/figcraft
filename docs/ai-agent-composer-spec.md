# AI Agent composer drawer with live editable canvas execution

Date: 2026-11-11. Status: feature specification with owner-confirmed desktop E2E review gate and approved four-ticket breakdown. Four local tickets are marked `ready-for-agent`; implementation and E2E review have not run. No remote issues have been published.

For another implementation or review session, begin with the [context pack](ai-agent-composer-context/README.md): product decisions, source findings, reference research, workspace behavior, execution reasoning and mandatory desktop E2E guidance. It supplies rationale and evidence without changing this behavioral contract.

## Problem Statement

Designers must currently switch between FigCraft's manual editor and an external agent to generate or revise designs. The engine already exposes native document operations, but the editor has no integrated composer connecting user intent, canvas context, a local agent harness and visible tool execution.

The requested outcome is an in-app composer drawer that genuinely creates and changes editable FigCraft designs. A conversation-only panel, generated code block, raster mockup or scripted demo response does not satisfy this need. Users also need confidence that the agent targets the intended design, preserves their other work and reports failures honestly.

The owner confirmed installed CLI harnesses with Codex first and Claude Code next. This specification concerns FigCraft's canvas; external Figma editing is not required.

## Solution

Extend FigCraft's existing two-wrapper left workspace: the narrow navigation rail at the far left and the resizable/collapsible content panel beside it. The rail order is **Menu, AI Chat, File, Assets, Variables**, as clarified by the owner. File retains pages/layers; Assets retains components and existing asset/library access. AI Chat contains conversation and sessions-list subviews; Sessions is not another top-level rail item. The property inspector remains on the right. A persistent bottom composer is available across expanded non-modal panel views.

A designer selects a frame or chooses to create a new design on the current page, writes a brief, chooses a supported installed harness/model and sends the request. The sidebar shows target context, attachments, text streaming, real tool activity, any required approvals, Stop and the resulting changes.

The harness receives FigCraft's original design instructions, relevant document/component/variable context and validated native design tools. It can inspect the target, create frames/text/shapes, configure auto layout, reuse components and variables, render the result and refine it. Successful tool edits appear live as ordinary editable layers on the canvas. The user can continue manually, request follow-up edits, accept the task's changes or reject them with explicit conflict handling.

The central workflow is brief and context → inspect → compose native changes → render and inspect → refine within the run's limits → present changes for review. FigCraft manages document authority and review; the existing harness manages model communication, conversation context and its agent loop.

34. As a designer, I want a new conversation to have separate context, so that unrelated tasks do not inherit each other's assumptions.
35. As a designer, I want prior conversations and interrupted tasks recoverable after restart, so that I can understand what happened without replaying edits.
36. As a designer, I want generated layers to survive save/reopen with their relationships intact, so that the result remains a normal FigCraft document.

## Implementation Decisions

- **Accepted delivery direction:** use installed executables, Codex first and Claude Code next. First delivery must meet the full Codex composer-to-edit contract; Claude support is a subsequent adapter, with no active but nonfunctional choice in the first delivery. Do not introduce a FigCraft-owned direct model/provider loop.
- **Accepted two-wrapper structure:** preserve the far-left navigation rail and the adjacent content panel. Add AI Chat between Menu and File, yielding Menu → AI Chat → File → Assets → Variables. Use the current rail's active/hover/accessibility conventions, resize/collapse controls and supported mirrored-layout behavior. Do not replace the rail with Pen's horizontal switcher or add a second top-level navigation system. Use original icons and accessible names.
- **Navigation semantics:** AI Chat opens the agent content panel; File retains pages/layers and Assets retains its existing component/asset workflows. Menu continues to open the main-menu popup. Variables continues to open the existing variable editor; source inspection currently shows it as a separate editor rather than a File/Assets-style content tab. This specification does not require moving Variables into the panel. Menu/Variables actions preserve the underlying selected panel and composer state. New Slides functionality and third-party library catalogs are not prerequisites.
- **AI Chat subviews:** the conversation view contains text, tool activity and review entry points. A sessions/history control inside AI Chat opens its sessions list, which contains identifiable conversations, actual run status and explicit New/Resume actions. Viewing this list does not switch a harness session. Selecting a conversation restores the conversation subview and revalidates its document binding before another request. Sessions is an AI Chat subview, not a sixth rail item.
- **Persistent composer/state:** keep the composer visible below expanded non-modal content views, including AI Chat conversation/sessions, File and Assets. Preserve draft text, attachments, selected harness/model, pending permissions and conversation identity across navigation; opening/closing Menu or the variable editor does not discard them. Retain per-view scroll/search/expansion state for the open workspace. Layer selection may update unsent context, but cannot retarget an active task. Submitting from File or Assets activates AI Chat's matching conversation without discarding the previous panel's navigation state.
- **Drawer behavior:** allow resize and collapse/reopen while preserving mode, width, conversation and document identity. Keep the property inspector on the right; Agent does not replace it. At narrow widths, collapse side panels through existing visibility controls and keep them recoverable without moving Agent to the right. Closing/collapsing the sidebar or switching modes does not stop or start a run. Keep running status and a reachable Stop entry available when the composer is hidden; identify which task it affects. Restore focus to the invoking control when closed. Use existing theme tokens, widgets, translation/accessibility patterns and original icons.
- **Input behavior:** provide a visible Send button, Enter to submit and Shift+Enter for a newline, respecting active IME composition. Disable duplicate submission while that conversation has an active turn. Permit drafting follow-up text while work runs; sending it waits until a subsequent explicit submission. Show Stop while active. No global key binding may take ordinary canvas shortcuts while text input owns focus.
- **Module responsibilities:** introduce a native Rust harness supervisor and adapter; extend editor presentation/app-state, task admission and review capabilities; reuse the engine, MCP tools and rendering modules. Keep subprocess work off the UI thread and out of document/layout/render modules. Keep dependency layering explicit.
- **Codex protocol:** use the documented app-server stdio interface. Initialize the owned connection, open/resume a thread, start turns, consume events, handle supported requests and interrupt turns. Match protocol capabilities/schema to the supported installed version. Model/auth/session management stay with Codex; no credential-file copying or silent edits to global harness configuration.
- **Session identity:** bind separate application conversation/task IDs, harness thread/turn IDs, document UID, page ID and target node IDs. Closing a document or deleting its target produces a visible unavailable/conflict outcome. A conversation switch does not retarget in-flight tool calls. Allow one mutating run per document initially; do not imply parallel design-agent support.
- **Scope:** support editing an explicit selected subtree and creating a new root design on an explicitly chosen page. Creation authority covers the new root and its descendants; existing sibling subtrees remain outside it. Context reads may include relevant design-system definitions without granting mutation authority to those definitions. A broader edit requires an explicit new scope decision.
- **Bootstrap:** provide a compact target snapshot with revision, outline, selected properties, available fonts and relevant components/variables. Include only attached references and relevant document information. Refresh stale context after external changes; do not assume a snapshot stays current for the whole conversation. Limit input size and report omitted context.
- **Tool exposure:** configure FigCraft's MCP endpoint for the harness session and verify successful tool initialization before marking it ready. Do not rely on the client automatically loading MCP prompts/resources. Supply a short original bootstrap explicitly and make deeper command/schema/design guidance retrievable through the existing MCP guidance surfaces.
- **Native tool vocabulary:** reuse structured inspection, command discovery, node creation, property updates, bounded batches and rendering. Components/variables/layout use registered engine commands. Tool schemas and guidance must match the running engine. Do not add a second document mutation vocabulary or unrestricted JavaScript execution tool to imitate another product.
- **Authority:** a host-issued task identity controls admission at the actual live-app execution point. An agent display name, tool annotation or self-declared task field is not authority. Validate command effects and nested batches against the task's document/scope; reject bypasses through generic command dispatch, global undo/redo, pointer/key/text automation or an unscoped control connection. File, clipboard, shell and network effects do not inherit permission from canvas-edit scope.
- **Actual execution:** validated tool calls create or edit native scene-graph objects through the existing attributed command path. Commit each coherent bounded edit group as one undo step and return real result IDs/errors. Update the visible canvas from committed engine state; a streamed tool argument is not an applied edit.
- **Visual methodology:** ship original design guidance for understanding the brief, defining hierarchy, typography, spacing, palette, layout and component reuse. Derive values from the user's design system and requested direction. Generate meaningful content and handle empty/loading/error states where requested. Avoid imposing one card/grid/palette recipe on every brief. This is runtime guidance for the designing agent, distinct from a repository-development skill.
- **Design-system use:** inspect and reuse actual component references and variable bindings where requested. Report missing resources; do not silently claim reuse after substituting similar-looking shapes/colors. New original resources must be explicitly task-owned and within scope.
- **Feedback loop:** after meaningful edit groups, inspect structure; render the affected frame and supply the actual image to a vision-capable model for critique/refinement. Never substitute a file path, tool-success message or text-only dimensions for an image the model saw. For a non-vision model, keep the rendered preview available to the user and report visual verification as unavailable. Stop refinement at the harness/run limits and report remaining defects.
- **Progress and completion:** represent readiness, running, awaiting input/permission, stopping, failed, interrupted and reviewable outcomes honestly. Surface only observable tool activity/status, not fabricated planning stages. Harness turn completion and user acceptance are separate; committed edits remain pending review until disposition. Usage is reported only when supplied; unknown usage stays unknown. Do not expose hidden reasoning.
- **Stop and uncertain outcomes:** first revoke admission for future mutations, then request supported harness interruption. A committed command stays committed until reviewed; an in-flight command that cannot be cancelled may finish and must be reconciled before reporting the settled result. Repeated Stop is safe. Process termination is distinct from turn interruption; use bounded shutdown and disclose unconfirmed interruption.
- **Failure and retry:** distinguish missing executable/auth/model, malformed protocol, tool rejection, render failure, process exit and lost replies. Never replay an uncertain mutation automatically. Inspect current state to reconcile it; require explicit retry where safe reconciliation is unavailable. Test fixtures are never a production fallback.
- **Review:** record task-owned changed nodes/properties and edit groups. Accept records disposition without reapplying edits. Reject applies safe task inverses while preserving intervening unrelated human changes. Same-property overlaps, dependent references and changes to task-created objects yield explicit conflicts where automatic rejection would lose work. Whole-document snapshot restoration and blindly undoing the last N steps do not meet this requirement.
- **History and recovery:** persist bounded task/conversation display state and harness references in application state, separately from shared design files. Use atomic writes and existing settings-location conventions. Cap retained text/attachment data and expose a clear-history action. On restart, mark nonterminal runs interrupted/unknown as appropriate; do not send a model request or replay edits automatically. Revalidate document identity, scope and review records before resuming.
- **Permissions:** show supported harness requests with their action and target; route the user's response by the original request ID. A denied or unsupported request does not become success. Document text, images, comments and fetched tool data cannot broaden authority. The canvas-design workflow requires no blanket shell/file/network permission; any external action remains separately authorized and capability-gated.
- **Platform behavior:** native adapters use owned subprocesses and bounded streams. Keep WASM builds working and present a truthful local-harness-unavailable state there. No Electron/Tauri/webview shell or handwritten JavaScript/TypeScript is introduced into the native application.

## Testing Decisions

- **Primary feature seam, confirmed by the owner:** use `agent-desktop` in the review session to operate the ordinary composer in the running FigCraft app, cross a real local-harness/MCP attachment and assert the resulting native document plus rendered frame and visible task state. This is the highest behavior seam: prompt in, editable design and review outcome out. Reuse existing UI/control/document/render interfaces; no new scene simulator or second command engine.
- **Mandatory review-session gate:** build and launch the identified implementation candidate, then use `agent-desktop` accessibility/input operations to open AI Chat, choose the real configured harness/model, enter an original synthetic brief and submit through the visible composer. Observe actual streamed tool activity and canvas changes. Direct MCP/control calls may supplement document assertions but cannot substitute for traversing the user-facing UI. Fixtures, unit/integration tests and the agent's own completion message cannot satisfy this gate.
- **Review both interfaces and generated design:** inspect window screenshots against the agreed two-wrapper layout and rail order, persistent composer, Sessions inside AI Chat, right inspector, focus/input, sizing and honest loading/error/permission/run states. Separately inspect the generated frame against its brief/reference and the visual acceptance rubric; verify editable native structure, real components/variables where requested, and save/reopen. Good generated artwork does not excuse broken editor controls, and a polished composer does not prove correct design generation.
- **Review scenarios and evidence:** exercise each ticket's applicable creation/edit/refinement/session/Stop/review/recovery flows in the real app; perform the full combined scenario set at final feature review. Record candidate commit/build, app/CLI/model versions, synthetic brief, actual desktop actions, before/after screenshots, document assertions and per-scenario pass/fail/blocker notes. Keep proprietary reference captures local; attach only original synthetic evidence that may be shared. Record defects, fix them and rerun affected scenarios against the revised candidate before marking them passed.
- **Missing prerequisites:** if desktop permissions, a runnable candidate, authentication or an authorized real model are unavailable, report the affected E2E scenario as blocked/unverified and the ticket as not review-complete. Do not replace this requirement with mocked model output, API-only execution, screenshots from another build or a claim that CI alone is sufficient. This is an acceptance requirement for review; no model calls are being run while drafting tickets.
- Good tests assert external outcomes and invariants, not implementation classes, function names, canned transcripts, exact model wording or the existence of a button. An implementation that only streams chat or displays a raster must fail feature acceptance.
- Reuse prior art: synthetic engine sessions and command/batch rollback tests; UI input-frame/accessibility tests; existing control/capture tests; attached MCP backend tests; retained-render versus full-render comparisons. Existing fake-app attachment tests are useful but insufficient for a real running-window/model workflow.
- Add narrowly scoped supervisor protocol tests behind the existing/new process interface where failures cannot be induced reliably end to end: malformed/oversized output, missing executable, early exit, duplicate events, unsupported capabilities, pending approvals and interruption. Use a controllable subprocess fixture, not a fake production agent.
- **AT01 — Drawer and readiness:** open/resize/collapse/reopen the left sidebar while the right inspector remains usable, without losing document/selection or an active run; test keyboard/IME behavior and constrained widths. Missing executable/auth/model and MCP initialization failure show specific actionable states. Opening the sidebar sends no inference request.
- **AT02 — Generate from an empty page:** with an authorized real Codex/model, request an original dashboard or mobile screen. Assert a new task-owned frame contains individually editable text/shapes, usable native layout and no unrelated page edits. Render and manually inspect it; save/reopen and inspect the same relationships.
- **AT03 — Edit an existing target:** select a synthetic component-based frame with variables, request a specific layout/content change, and assert actual requested edits, instance/binding preservation and untouched siblings. Switch tabs and selection during the run; confirm the original target remains authoritative.
- **AT04 — Tool-to-canvas evidence:** correlate a successful tool result with real created/changed node IDs and a canvas update. Partial argument streaming, rejected calls and failed tools must not show invented applied edits or successful completion.
- **AT05 — Visual refinement:** use a fixture with known clipping/overflow or a requested hierarchy correction. Confirm an actual affected-frame image reaches a vision-capable model, the resulting design is inspected and the final result is re-rendered after any correction. A non-vision model cannot receive a visually-verified status. A screenshot alone does not establish aesthetic quality.
- **AT06 — Scope and batch enforcement:** attempt wrong-document, sibling/ancestor/design-system-definition edits, nested-batch escapes and equivalent mutations through generic commands or UI automation; reject them without target changes. Fail a later step in a bounded batch and assert no partial document edits from that group remain.
- **AT07 — Stop and uncertain replies:** interrupt between edit groups and while a result is in flight. Confirm no new task mutation is admitted after Stop, retained edits are accurately listed, settled interruption is distinguishable from an unconfirmed outcome, and follow-up/retry does not duplicate objects.
- **AT08 — Review with human edits:** interleave an unrelated human edit, accept once and reject once in separate scenarios. Reject preserves human work. Edit a task-owned property or dependent reference manually and verify conflict handling rather than snapshot restoration or data loss.
- **AT09 — Failure/recovery:** exercise tool errors, render failure, authentication loss, harness exit, target closure/deletion and app restart. Preserve truthful states and valid committed edits; no automatic inference request or mutation replay on recovery. Show incomplete verification explicitly.
- **AT10 — Conversation and permissions:** resume a conversation with correct identities, create a separate conversation, deny a permission request and attempt scope escalation via attachment/document instructions. Assert isolation, correct request routing and no credential leakage in design files, tool output or task history.
- **AT11 — Editor/platform regression:** verify ordinary drawing, inspector, shortcuts, undo/redo and save/reopen; inspect light/dark, narrow widths, scaling, focus/accessibility and reduced motion. Native UI remains responsive while the harness runs. Compile/check the existing WASM target and confirm its truthful unavailable state.
- **AT12 — Navigation rail, content panel and sessions:** assert the rail order Menu → AI Chat → File → Assets → Variables, preserving the existing menu and variable-editor behavior. Compose a draft with an attachment, switch AI Chat → File → Assets, open/close Variables and Menu, then return to AI Chat and switch between its Sessions and conversation subviews. Assert preserved draft/model/context/conversation, panel width and per-view navigation state. Confirm the composer remains visible in expanded non-modal content views and the property inspector remains independently usable. Sessions is not a top-level rail entry. Resume a listed conversation and verify the intended thread/document; merely browsing Sessions does not start a turn. Switch panels/collapse during a real run, assert continued task identity and reachable Stop, then return to its actual activity/review state. Layer selection changes must not retarget that run.
- **Visual acceptance rubric:** a reviewer checks adherence to the brief/reference direction, readable type hierarchy, consistent spacing/alignment, absence of unintended clipping/overlap, meaningful content and requested component/variable reuse. Record pass/fail and remaining defects against the chosen synthetic brief. Avoid claiming that one prompt or one tool interface guarantees attractive UI for arbitrary requests.
- Record candidate commit/build, native platform, CLI/protocol version, actual model/capabilities, fixture/brief, tool outcomes, native document assertions and reviewed screenshots. Use original synthetic content. Real inference requires spending authorization; no such call is authorized merely by drafting this spec.
- Before a landed implementation, run the relevant regression tests and repository quality gates, including formatting, Clippy, tests, layers, assets/docs and WASM. Report only checks actually run. A green protocol fixture does not mark real-model acceptance complete.

## Out of Scope

- Creating or installing the proposed egui-development repository skill.
- A custom direct-to-model agent engine, model training or bundling/updating harness binaries.
- External Figma automation; the target is FigCraft's native editable canvas.
- Browser sidebar, embedded browser, website import/reconstruction and browser-based local-process bridges; these remain separate specifications.
- Parallel agents, unattended repeated alternatives and automatic cross-document task execution.
- New Slides functionality or third-party design-library catalogs merely because those modes exist in the reference product; preserve FigCraft's existing design capabilities.
- Arbitrary repository/code-writing, code deployment, general-purpose shell/file/network automation or configuring additional third-party MCP servers.
- Raster-only generation as a substitute for editable designs; copying proprietary product code, prompts, artwork, icons or templates.
- Full application implementation/export fidelity guarantees from generated design layers.
- Removing existing safety checks, changing shared CI or broadly refactoring the editor outside the feature's needs.
